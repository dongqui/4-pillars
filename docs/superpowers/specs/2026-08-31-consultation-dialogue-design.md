# 고민상담 — 대화 설계 가이드

날짜: 2026-08-31
목적: 사주 기반 고민상담의 답변 원칙, 질문 정책, 운 해석 범위, UI/대화 구조

> **[2026-08-17 고민상담(채팅) 설계](2026-08-17-consultation-chat-design.md)와의 관계**
>
> 그 문서는 **무엇을 만드는가**(데이터 모델·이용권·캐시 경계·화면·비용 상한)를 정한다.
> 이 문서는 그 위에서 **상담사가 어떻게 말하는가**를 정한다. 둘 다 살아 있고 절 번호가
> 겹치므로, 코드 주석에서 이 문서를 가리킬 때는 **`대화 설계 §N`**, 그 문서를 가리킬 때는
> **`설계 §N`** 으로 적는다.

---

## 1. 기능의 핵심 방향

고민상담은 일반적인 AI 위로나 생활 조언을 사주 UI에 넣는 기능이 아니다. 핵심은:

> 사용자의 고민을 먼저 이해하고, 실제 사주 데이터에서 확인되는 패턴을 해석의 렌즈로
> 사용해 현재 상황을 함께 좁혀가는 상담

두 극단을 피한다.

**피해야 할 A — 일반 AI 상담**
"그럴 수 있어요. 작은 목표부터 시작해보세요." → 사주 서비스만의 이유가 약하다.

**피해야 할 B — 운명론적 사주 상담**
"당신은 원래 절제가 약한 사주입니다." → 현재 행동과 상태를 타고난 운명으로 단정한다.

**지향**

> 사주에서는 한번 방향을 잡으면 오래 밀어붙이는 힘이 강하게 보여요.
> 그래서 지금 문제를 단순히 '의지가 약해서'라고 보기보다, 이미 한쪽으로 굳어진 흐름을
> 어떻게 끊을지가 더 중요해 보여요.

사주 → 현재 고민과 연결 → 현실적인 조언.

## 2. 수정할 표현

다음 같은 표현은 피한다.

> 타고난 기질이 단단해서 한번 빠지면 멈추기 어려운 쪽이에요. 술도 그렇고, 쉬는 것도 그렇고.

- 어떤 사주 근거에서 나온 말인지 알 수 없다.
- 거의 누구에게나 붙일 수 있다.
- 술을 조절하기 어려운 상태를 '타고난 기질'로 설명한다.
- 사주가 현재 상태의 직접적 원인인 것처럼 단정할 위험이 있다.

상담에서는 **실제로 제공된 사주 사실과 연결 가능한 내용만** 사용한다.

## 3. 기본 답변 구조

항상 같은 형식일 필요는 없지만 기본 사고 순서는 다음과 같다.

1. 사용자의 고민 이해
2. 이번 고민과 관련 있는 사주 근거 선택
3. 사주에서 보이는 패턴을 쉬운 언어로 설명
4. 현재 고민과 연결
5. 필요한 경우 현실적인 제안
6. 추가 정보가 꼭 필요할 때만 질문

질문은 대화를 유지하기 위한 장치가 아니라 **다음 해석의 정확도를 높이기 위한 정보 획득
장치**다.

## 4. 매번 질문으로 끝내지 않는다

항상 질문으로 끝나면 상담이 아니라 문진표가 된다.

| 상황 | 질문 여부 | 이유 |
| --- | --- | --- |
| 고민이 너무 넓고 원인이 섞여 있음 | 질문 | 무엇을 먼저 볼지 좁힐 필요가 있음 |
| 사용자 답에 따라 다음 해석이 크게 달라짐 | 질문 | 필요한 분기 정보가 있음 |
| 사용자가 감정만 아주 짧게 털어놓음 | 필요할 때만 | 더 이야기할 지점을 찾기 위함 |
| 이미 충분한 정보가 있음 | 하지 않음 | 바로 해석하거나 제안할 수 있음 |
| 사용자가 명확한 질문을 함 | 우선 하지 않음 | 먼저 그 질문에 답함 |
| 실행 가능한 작은 제안을 이미 제공함 | 하지 않아도 됨 | 자연스럽게 마쳐도 됨 |
| 직전 AI 답변도 질문으로 끝났음 | 가급적 하지 않음 | 연속 문진 느낌을 줄임 |

**프롬프트 원칙**

- 답변 끝에 습관적으로 질문하지 않는다.
- 다음 해석이나 조언의 방향이 사용자의 추가 정보에 따라 의미 있게 달라질 때만 질문한다.
- 이미 충분한 정보가 있다면 해석·공감 또는 작은 제안으로 자연스럽게 마무리한다.
- 연속된 두 AI 답변을 모두 질문으로 끝내는 것은 특별한 이유가 없는 한 피한다.
- 질문할 경우 한 번에 하나만, 답하기 쉽고 구체적으로 묻는다.

**연속 질문 억제는 기본값이지 절대 규칙이 아니다**

> AI: 언제부터 이런 느낌이 있었어요?
> 사용자: 한 두 달 된 것 같아요.

여기서는 대개 질문 없이 답하는 게 맞다. 그런데 사용자가 "한 두 달 됐는데 최근에는 잠도
거의 못 자요" 처럼 **새로운 중요한 정보를 얹었다면** 다시 확인해야 할 수도 있다. 그래서
꼬리 지시는 "되묻지 마라"가 아니라 "되묻지 말고 해석이나 작은 제안으로 맺는 것을 기본으로
삼되, 안전에 관계되거나 새로 나온 정보를 확인하지 않으면 해석이 틀어지는 경우에는 물어도
된다"로 준다.

**판정은 문자열이 아니라 메타데이터로 한다**

물음표 유무로 짐작하면 양쪽으로 틀린다.

- "어느 쪽이 더 가까운지 말해줘요." → `?` 없이 답을 요구한다.
- "'내가 왜 이러지?' 라는 생각이 들 수 있어요." → `?` 가 있지만 되묻는 게 아니다.

그래서 답을 만든 쪽이 직접 표시한다. 응답 스키마에 `asks_user: boolean` 을 두고
(`consultation_messages.asks_user` 로 저장), 다음 턴은 그 값을 읽어 억제 지시를 건다.
컬럼이 생기기 전에 쌓인 행(`null`)에서만 물음표 짐작으로 물러선다.

## 5. 대화 턴의 역할을 구분한다

모든 답변을 `공감 → 설명 → 질문` 패턴으로 만들지 않는다.

- **A. 탐색** — 고민이 아직 넓거나 정보가 부족할 때. 어느 쪽인지 좁힌다.
- **B. 해석** — 답을 바탕으로 사주에서 보이는 패턴을 설명한다. 질문으로 끝낼 필요 없다.
- **C. 제안** — "그럼 어떻게 해야 하나요?"에 구체적이고 작은 제안을 준다. 질문 불필요.
- **D. 수용 / 재탐색** — 제안이 어렵다고 하거나 새 정보가 왔을 때. 기준을 낮추거나 다시 탐색.

## 6. 질문 밀도

질문 비율을 **코드에서 랜덤 확률로 결정하지 않는다.** 결과적으로 질문이 들어가는 턴은
소수여야 한다(UX 감각으로 30~40% 정도). 이는 목표 감각이지 고정 확률이 아니다.

판단 기준은 언제나 하나다: **이 질문에 대한 답이 있어야 다음 해석이 의미 있게 달라지는가?**

## 7. 사주 기반 답변은 필수다

몇 번 대화한 뒤 "이거 그냥 일반 ChatGPT 상담 아닌가?"라고 느껴서는 안 된다. 상담의 핵심
해석에는 **반드시 제공된 사주 사실 중 하나 이상의 근거**가 있어야 한다. 다만 모든 문장에
명리 용어를 붙일 필요는 없다.

## 8. 사주 해석층과 상담 답변층을 분리한다

LLM에게 원국 전체를 던지고 즉석에서 그럴듯한 말을 만들게 하지 않는다.

**8.1 사주 해석층** — 이번 고민과 관련 있는 사주 사실을 먼저 추린다(일간·신강도·비겁/식상·
현재 대운·올해 세운 …). 이 가운데 직접 관련 있는 근거만 1~3개 선택한다.

**8.2 상담 답변층** — 선택한 사실을 바탕으로 사용자 언어로 답변을 만든다.

```
사용자 고민 → 관련 사주 요소 선택 → 그 요소가 의미하는 경향 설명
           → 현재 고민과 연결 → 현실적인 제안 → 필요할 때만 질문
```

## 9. 사주 사실을 만들어내지 않는다

- 사용자의 사주 정보에서 확인되지 않는 성향이나 운세를 만들어내지 않는다.
- 핵심 해석에는 반드시 제공된 사주 사실 중 하나 이상의 근거가 있어야 한다.
- 고민과 관련 없는 사주 요소를 억지로 언급하지 않는다.
- 사주는 성향과 흐름을 해석하는 참고 틀이며, 현재 상태의 **직접적인 원인으로 단정하지 않는다.**

특히 술·건강·무기력처럼 현실적 원인이 큰 주제에서 다음은 금지한다.

- "이번 달 운 때문에 술을 많이 마시게 됩니다."
- "당신은 원래 중독되기 쉬운 사주입니다."
- "이번 달 재물의 힘이 강하게 들어와 있어서 술을 더 찾게 되는 시기예요."

이 금지는 사실 블록 안에도 한 줄로 박아 둔다.

```
※ 흐름은 고민의 원인을 단정하는 근거가 아니다. 상대가 말한 지금 상태와 이어 읽을 수는
  있어도, 몸·감정·행동의 변화가 이 흐름 때문에 생겼다고 말하지 마라.
```

**원국 = 성향의 렌즈, 운 = 시기의 렌즈.** `운 = 현재 문제의 원인` 이 되면 안 된다. 원하는
것은 "원래의 패턴과 견주면, 지금은 이런 성향이 조금 더 두드러질 수 있는 흐름으로 읽혀요"
정도다.

## 10. 사용자에게는 명리 용어를 번역해서 보여준다

| 직접적인 명리 용어 | 권장 표현 |
| --- | --- |
| 비겁이 강하고 식상이 약해서… | 스스로 밀고 가는 힘은 강한데, 힘을 자연스럽게 빼거나 다른 방향으로 전환하는 쪽은 상대적으로 약하게 나타나요. |

필요하다면 "왜 이렇게 봤나요?"로 근거를 따로 확인할 수 있게 한다. 기본 화면은 읽기 쉬운
상담, 상세 화면은 실제 명리 근거.

## 11. 모든 질문을 사주로 설명하지 않는다

| 고민 | 사주 활용 정도 |
| --- | --- |
| 이직을 고민하고 있어요 | 높음 |
| 친구와 자꾸 부딪혀요 | 높음 — 관계 패턴 포함 |
| 왜 결정을 자꾸 미룰까요 | 높음 |
| 최근 연애가 계속 꼬여요 | 높음 — 현재 운 포함 가능 |
| 감기약 뭘 먹어야 해요 | 거의 사용하지 않음 |
| 술을 너무 많이 마셔서 끊기 힘들어요 | 성향 참고까지만, 원인·진단은 단정하지 않음 |

## 12. 원국뿐 아니라 대운·세운·월운도 활용한다

```
원국      → 나는 원래 어떤 방식으로 반응하는가
대운/세운 → 왜 요즘 이런 문제가 더 두드러지는가
월운      → 왜 하필 지금 이 시점에 강하게 느껴지는가
```

**원래의 패턴 × 최근의 흐름.** 이 지점이 일반 AI 상담과의 중요한 차별점이다.

## 13. 고민에 따라 운 참조 범위를 다르게 한다

| 사용자 질문 | 기본 참조 범위 |
| --- | --- |
| 저는 왜 항상 이런가요? | 원국 중심 |
| 연애할 때 왜 자꾸 이런 사람이 끌리죠? | 원국 중심 |
| 요즘 유독 왜 이러죠? | 원국 + 대운 + 세운 |
| 최근 연애가 계속 꼬여요 | 원국 + 현재 대운/세운 |
| 올해 이직해도 될까요? | 원국 + 대운 + 세운 |
| 이번 달 옮기는 게 나을까요? | 원국 + 대운 + 세운 + 월운 |
| 다음 달 중요한 면접이 있어요 | 원국 + 대운 + 세운 + 해당 월운 |

시간성이 강해질수록 현재 운을 더 깊게 내려간다.

## 14. 운 참조 범위는 고정 Facts + 선택으로 간다

> **개정(2026-08-31).** 처음 초안은 "고민을 먼저 분류해 참조 범위를 앱 단계에서 고른다" 였다.
> 구현하면서 아래 쪽이 더 낫다고 판단해 문서를 고쳤다. §13 의 표는 여전히 유효하다 —
> 다만 그 표를 **앱이 아니라 상담사가** 적용한다.

```
원국 + 대운 + 세운 + 월운을 고정 Facts 로 제공
→ 상담사가 이번 질문과 관련 있는 근거만 선택
→ 답변에는 필요한 것만 노출
```

사전 분류기를 두지 않는 이유:

- 턴마다 LLM 호출이 하나 더 늘거나(비용 두 배) 키워드 규칙이 되는데, "요즘 유독" 이라는
  말이 없다고 시간성이 없는 것은 아니다.
- 더 중요한 이유: 사실 블록은 한 상담 안에서 **글자 하나 안 바뀌어야** prefix 캐시가 산다
  (설계 §3 의 캐시 경계). 분류 결과에 따라 블록이 턴마다 달라지면 캐시가 매 턴 깨지고,
  상담사가 근거로 삼는 것이 대화 중간에 바뀐다.
- §17 이 이미 "내부에서는 모두 계산하되 답변에는 필요한 것만 노출한다" 고 말한다. 이 구조는
  그 문장 그대로다 — 거르는 자리가 사실 블록이 아니라 프롬프트일 뿐이다.

**대신 프롬프트에 이 규칙이 강하게 있어야 한다.**

> 사주 사실은 답변의 근거이지 답변에서 전부 소비해야 하는 체크리스트가 아니다. 원국과 현재
> 흐름 중 사용자의 고민을 설명하는 데 실제로 필요한 요소만 사용한다. 현재 흐름이 제공되어
> 있다는 이유만으로 대운·세운·월운을 언급하지 않는다.

없으면 "나는 왜 사람한테 싫은 소리를 못 할까?" 같은 시점 없는 고민에도 매번 "현재 대운을
보면…" 이 붙어 바로 부자연스러워진다.

## 15. LLM에 넘기는 사실 블록 예시

```
[원국에서 이번 고민과 관련 있는 사실]
[현재 대운에서 관련 있는 사실]
[2026 세운에서 관련 있는 사실]
[2026년 8월 월운에서 관련 있는 사실]
```

대운·세운·월운을 구분해 전달한다. 구분이 없으면 LLM이 원래 성향과 일시적인 흐름을 섞는다.

## 16. 답변에서도 '원래의 나'와 '지금의 흐름'을 구분한다

> 원래도 한쪽으로 힘을 오래 밀고 가는 편인데, 올해는 그런 성향이 더 강하게 드러나기 쉬운
> 흐름이 겹쳐 있어요.

이렇게 하면 사용자가 현재의 어려움을 고정된 운명으로 받아들이는 것을 줄일 수 있다.

## 17. 내부에서는 모두 계산하되, 답변에는 필요한 것만 노출한다

대운·세운·월운을 모두 계산해두는 것은 좋다. 하지만 답변에서 매번 나열하면 상담이 아니라
명리 리포트가 된다. **이번 고민을 설명하는 데 가장 중요한 1~2개 근거만** 사용한다.

## 18. 빠른 답변(Quick Reply) 정책

매 턴 필수가 아니다. 특히 AI가 방금 제안한 내용을 그대로 수용하도록 유도하는 버튼은 피한다
("작은 것부터 다시 해볼게요"). 실제 대화 분기가 필요할 때 사용한다("술 조절이 제일
어려워요" / "그냥 다 하기 싫어요"). 선택지를 억지로 항상 2개씩 노출할 필요는 없다.

## 19. "요즘 특히 몸이 무거워요"는 완전히 제거

- 다른 위치로 이동하지 않는다.
- 유사 표현으로 바꾸어 유지하지 않는다.
- 기본 빠른 답변 예시에서도 제외한다.

필요하면 해당 슬롯 자체를 없애거나, 실제 분기에 의미가 있을 때만 새 빠른 답변을 표시한다.

## 20. UI / 대화 리듬

**20.1 AI 말풍선 연속 출력 최소화** — 3개가 연속으로 쌓이면 리포트 조각을 채팅창에 나누어
붙인 느낌이 난다. `공감 + 해석`을 하나로 묶고, 필요할 때만 두 번째에서 제안 또는 질문.

**20.2 "남은 대화 9회"** — 상담 몰입을 깨지 않게 존재감을 낮춘다. 제목 아래에 강하게 두기보다
메뉴 안, 입력창 근처의 작은 상태 표시, "9회 남음"처럼 짧은 표현을 검토한다.

## 21. 예시 — 질문이 필요한 경우

> 자기 절제가 잘 안 됩니다. 술도 계속 들어가고.. 운동하기도 싫고

여러 가능성이 섞여 있다(술 조절 / 전반적 의욕 저하 / 운동만 / 생활 리듬). 첫 턴에서는
방향을 좁히는 질문이 가치가 있다.

> 사주에서는 한번 방향이 잡히면 오래 밀고 가는 힘이 강한 편으로 보여요. 그래서 지금도 단순히
> 의지가 약하다기보다, 이미 익숙한 흐름에서 빠져나오는 데 시간이 걸리는 쪽에 가까울 수 있어요.
> 그런데 술을 조절하기 어려운 게 더 큰가요, 아니면 요즘 전반적으로 아무것도 하기 싫은 느낌이
> 더 큰가요?

## 22. 예시 — 질문이 필요하지 않은 경우

> 그렇다면 지금은 생활 전체를 한꺼번에 바로잡으려고 하기보다 한 가지 기준만 먼저 세우는 편이
> 더 맞아 보여요. 사주에서도 한 번 방향이 잡히면 오래 가는 힘이 있는 편이라, 시작점을 작게
> 잡는 게 오히려 중요해요. 오늘 운동까지 챙기려 하지 말고, 하나만 정해서 지켜보는 식으로요.

여기서 자연스럽게 끝낸다.

## 23. 상담 답변 생성용 핵심 프롬프트 초안

```
[사주 근거]
- 상담의 핵심 해석에는 반드시 제공된 사주 사실 중 하나 이상의 근거를 사용한다.
- 제공되지 않은 사주 성향, 구조, 운세를 만들어내지 않는다.
- 고민과 관련 없는 명리 요소를 억지로 언급하지 않는다.
- 사주 사실은 답변의 근거이지 전부 소비해야 하는 체크리스트가 아니다.
  현재 흐름이 제공되어 있다는 이유만으로 대운·세운·월운을 언급하지 않는다.
- 원국의 성향과 대운·세운·월운의 일시적 흐름을 구분한다.
- 현재 상태의 원인을 사주로 단정하지 않는다.

[표현]
- 전문 명리 용어를 나열하기보다 이해하기 쉬운 언어로 번역한다.
- 결정론적 표현, '당신은 원래 OO할 수밖에 없다' 같은 표현을 쓰지 않는다.

[질문]
- 답변 끝에 습관적으로 질문하지 않는다.
- 다음 해석이나 조언이 추가 정보에 따라 의미 있게 달라질 때만 질문한다.
- 이미 충분하면 해석·공감·제안으로 자연스럽게 끝낸다.
- 연속된 두 답변을 질문으로 마무리하지 않는 것을 기본으로 한다.
- 질문은 한 번에 하나, 구체적이고 답하기 쉽게.

[조언]
- 사주 해석만 늘어놓지 말고 현재 고민과 연결한다.
- 행동 제안은 작고 현실적인 수준으로.
- 의료·중독 등 전문적 판단 영역의 원인을 사주로 설명하거나 진단하지 않는다.
```

## 24. 구현 관점의 파이프라인

> **개정(2026-08-31).** §14 와 같은 이유로 사전 분류 단계를 뺐다.

```
프로필 → 원국 + 대운 + 세운 + 월운을 한 벌의 고정 [사실] 블록으로 (상담 내내 불변)
       ↓
사용자 메시지 + 직전 턴의 asks_user → 꼬리 지시(남은 턴 · 되묻기 억제 · 마무리)
       ↓
상담사가 관련 근거 1~2개 선택 → 턴 역할 결정(탐색·해석·제안·수용/재탐색)
       ↓
답변 생성 → asks_user 표시 → 갈래가 있을 때만 Quick Reply
```

앱이 결정론적으로 정하는 것은 **꼬리**뿐이다(남은 턴 수, 되묻기 억제 여부, 마지막 턴
지시문). 나머지 판단은 상담사에게 맡기되, 개수와 필수 여부는 프롬프트가 아니라 **tool
스키마**로 못 박는다.

## 25. 최종 원칙 요약

1. 상담의 핵심 해석은 실제 사주 근거에서 출발한다.
2. 원국은 원래의 패턴, 대운·세운은 최근의 흐름, 월운은 구체적인 시점을 설명한다.
3. 대운·세운·월운은 내부에서 계산하되 답변에는 필요한 근거만 노출한다. 사실은 답변의
   근거이지 전부 소비해야 하는 체크리스트가 아니다 — 제공되었다는 이유만으로 언급하지
   않는다.
4. 사주를 현재 상태의 직접적 원인으로 단정하지 않는다.
5. 매 답변을 질문으로 끝내지 않는다.
6. 질문은 다음 해석에 실제로 필요한 정보가 있을 때만 한다.
7. Quick Reply도 실제 분기가 필요할 때만 사용한다.
8. "요즘 특히 몸이 무거워요" 문구는 완전히 제거한다.
9. 일반 AI 상담과 차이가 느껴지되, 과도한 명리 전문용어 나열은 피한다.
10. '사주가 답을 내려주는 상담'보다 **'사주라는 렌즈로 고민을 함께 좁혀가는 상담'** 을 지향한다.

**프롬프트가 아니라 스키마로 막은 것**

부탁은 지켜지지 않는 날이 온다. 그래서 개수와 필수 여부는 tool 파라미터 스키마에 박는다.

- `bubbles` 1~3개
- `user_replies` 0~2개 (마지막 턴은 `maxItems: 0`)
- `asks_user` 필수, 마지막 턴은 `enum: [false]`
- `title` 은 첫 턴에만 필수

**아직 안 한 것**

- §10 의 "왜 이렇게 봤나요?" — 근거를 펼쳐 보는 상세 화면. 사실 블록은 이미 있으니 화면만
  붙이면 되지만, 명리 용어를 그대로 노출하는 화면이라 §10 의 번역 원칙과 어떻게 공존할지
  따로 정해야 한다.
- §11 의 "감기약 뭘 먹어야 해요" 류 — 사주를 거의 쓰지 않는 고민. 지금은 절대 규칙 3 이
  간접적으로만 막는다.
