# 관계 지도 UI 스파이크 (`/lab/relationship-world`) 설계 문서

**날짜:** 2026-08-16
**출처 브리프:** `project-saju-relationship-world-ui-spike.md` (사용자 제공)

## 1. 목표

관계 엔진도, 완성된 관계 지도도 만들지 않는다. 이번에 답할 질문은 하나다.

> **"관계 지도를 3D 공간으로 표현했을 때, 모바일에서 보기 좋고 직관적인가?"**

좋으면 확장하고, 별로면 2D/SVG로 돌아간다. **기술 검증이 아니라 제품 UI 검증이다.**

## 2. 범위 결정 (확정됨)

| 항목 | 결정 |
| --- | --- |
| 공간 메타포 | **우주.** 섬/지형은 결국 바닥 평면에 얹혀 y축이 장식이 된다. 5개 공간이 서로 다른 거리·고도·밀도를 갖는 3차원 부피로 존재한다. |
| 5개 공간의 형태 | **깊이가 다른 5개 성운(nebula).** 점이 아니라 들어갈 수 있는 영역. |
| 친구 수 | **20명.** 브리프는 5~8명이지만, 8명에서만 예쁜 관계 지도는 쓸모가 없다. 밀도 부하까지 함께 검증한다. (§6) |
| 카메라 | **A/B/C 3개 모드 + 화면 내 토글.** 브리프가 "실제로 비교한 뒤 결정"을 요구한다. (§9) |
| 사람 표현 | **DOM 마커 (`drei <Html>`).** WebGL 텍스트 아님. (§7) |
| 색 | **5개 공간을 색으로 구분하지 않는다.** (§5) |
| 데이터 | 목 데이터만. 실제 사주 계산·API·DB 없음. |

### 비범위 (YAGNI)

브리프 11절을 그대로 따른다 — 실제 Relationship DB, 프로필 저장/전환, 사람 추가 플로우, 십성 계산 연결, 15개 Archetype, 형/파/해/삼합, 궁합 점수, 60종 일러스트, 복잡한 terrain, shader, physics, WebGPU, 결제.

추가로 이번에 하지 않는 것:

- **접근성 전면 대응.** 마커에 `aria-label`과 키보드 포커스는 넣되, 3D 씬의 스크린리더 대체 표현은 만들지 않는다. 스파이크가 살아남으면 그때 설계한다.
- **성능 최적화.** 20명이 실제로 버벅이는지를 **관찰하는 것**이 이번 목적이다. 미리 최적화하면 판단 근거가 사라진다.
- **다국어.** 한국어 하드코딩. 다른 화면과 결을 맞춘다.

## 3. 라우트와 격리

```
src/app/lab/relationship-world/page.tsx
```

`/lab` 네임스페이스에 두는 이유는 두 가지다. 경로 자체가 "버려질 수 있는 코드"라고 말해주고, 이후 스파이크들이 같은 자리에 모인다.

| 항목 | 처리 |
| --- | --- |
| 진입 | 어디에서도 링크하지 않는다. URL 직접 입력만. |
| 색인 | `export const metadata = { robots: { index: false, follow: false } }` |
| 가드 | 없음. 로그인·프로필 불필요 — 목 데이터뿐이라 막을 것이 없다. |

### 다크 배경을 globals에 새게 하지 않는다

`src/app/globals.css`는 `color-scheme: light` + 흰 body다. 우주는 어두워야 하지만 **globals.css는 건드리지 않는다.** 이 라우트 전용 `layout.tsx` 안에서만 어둡게 감싼다. 스파이크가 프로덕션 화면의 색을 바꾸면 안 된다.

### 클라이언트 경계

`page.tsx`는 서버 컴포넌트로 두고 metadata만 내보낸다. 실제 화면은 `WorldShell.tsx`(`"use client"`)가 맡고, `<Canvas>`는 그 안에서 `next/dynamic` + `ssr: false`로 지연 로드한다. three는 `window`를 요구하므로 SSR 경로에 올리지 않는다.

> 구현 시 `node_modules/next/dist/docs/`에서 `dynamic` / `ssr: false`의 현재 규약을 먼저 확인한다. 이 Next 버전은 학습 데이터와 다를 수 있다 (AGENTS.md).

### 의존성

| 패키지 | 버전 | 비고 |
| --- | --- | --- |
| `three` | `^0.185.1` | |
| `@react-three/fiber` | `^9.7.0` | peer `react >=19 <19.3` — 프로젝트의 19.2.4와 맞는다 |
| `@react-three/drei` | `^10.7.8` | `<Html>`, `<OrbitControls>`, `<Points>` |

## 5. 월드

### 배경

순수 검정이 아니라 **DS의 잉크색 `slate-900 #0F172A`를 베이스로 한 깊은 남색 그라디언트**다. 검정은 우주지만 브랜드가 없다. `#0F172A`는 이미 이 서비스의 본문 색이라, 우주로 가면서도 기존 화면과 같은 집안으로 읽힌다.

### 깊이를 만드는 세 겹

1. **별먼지 3레이어** (near / mid / far) — 레이어마다 입자 크기·투명도·패럴랙스 계수가 다르다.
2. **5개 성운** — 거리 `r` 4~9, 고도 `y` −3~+4, 방위각이 모두 제각각.
3. **겹침** — 5개 중 최소 두 개는 카메라 기본 시점에서 **앞뒤로 겹치게** 배치한다.

셋째가 핵심이다. 겹치지 않으면 아무리 3D여도 평면 배치로 읽힌다.

### 색으로 구분하지 않는다

브리프 5절이 `木=초록` 같은 임의 의미색을 금지한다. 그래서 **5개 공간은 색이 아니라 명도·밀도·형태·크기로 구분한다.** 좁은 한색 계열(slate-400 ~ blue-200) 안에서만 미세하게 변주하고, 그 변주는 어떤 의미도 갖지 않는다.

화면에서 채도를 가진 요소는 **딱 하나, 중심의 `나` 코어**(accent `#2563EB` 계열 은은한 발광)다. 유일한 채도가 곧 시선의 기준점이 된다.

### 방향 감각 앵커

바닥 평면이 없으면 모바일에서 방향을 잃는다. 브리프 10절의 "카메라 때문에 길을 잃지 않게"를 위해 **거의 보이지 않는 황도면 disc** 하나를 깐다. 의식적으로 인지되지 않되 위/아래는 느껴지는 수준.

## 6. 목 데이터 — 나 1명 + 친구 20명

`src/lib/saju-core/data/characters-60.json`에 실제 일주 장면명이 있다(`갑자 → "깊은 물가의 큰나무"`). 이름을 새로 지어내지 않고 여기서 가져온다.

친구 한 명이 갖는 값은 브리프 3절대로 넷뿐이다.

```ts
type MockPerson = {
  id: string;
  name: string;            // 한글 2~3자
  pillarKey: string;       // "갑자"
  sceneName: string;       // characters-60.json에서
  role: RelationRole;      // 5개 중 하나
  feature: "none" | "yukhap" | "chung";
};
```

### 역할 배분은 고르지 않게

| 역할 | 인원 |
| --- | --- |
| 나를 채워주는 사람 | 6 |
| 나란히 서는 사람 | 5 |
| 나를 표현하게 하는 사람 | 4 |
| 나를 움직이게 하는 사람 | 3 |
| 나를 다듬는 사람 | 2 |

균등 배분은 차트처럼 보이는 지름길이다. 실제 인간관계도 고르지 않다.

`feature`는 六合 5명 / 沖 4명 / 없음 11명 정도로 흩는다. **없음이 다수여야 한다** — 六合·沖이 흔해 보이면 특징이 아니라 기본값으로 읽힌다.

## 7. 사람 — WebGL 텍스트를 쓰지 않는다

**`drei <Html>`로 DOM 마커를 띄운다.** three의 텍스트(troika)로 한글을 그리려면 폰트 파일을 따로 실어야 하고, 그렇게 해도 375px에서 한글 가독성이 DOM만 못하다. 이 스파이크의 1순위 판정 기준이 "이름을 읽을 수 있는가 / 터치하기 쉬운가"라, 44px 터치 타겟과 Pretendard를 그대로 쓸 수 있는 DOM이 압도적으로 유리하다. 브리프 6절의 "긴 한글 설명은 WebGL 안에 넣지 않는다"와도 같은 방향이다.

마커는 구체가 아니라 **얇은 명패(plate)**다. 이름 2~3자만 올린다. 장면명은 시트에서만 보여준다.

### 20명을 위한 LOD — 겹침이 진짜 문제다

20개 DOM 마커가 동시에 이름을 달면 375px에서 서로 겹쳐 뭉갠다. 카메라 거리에 따라 3단계로 떨어뜨린다.

| 단계 | 조건 | 표현 |
| --- | --- | --- |
| Full | 가까움 | 명패 + 이름 (44px 터치 타겟) |
| Compact | 중간 | 작은 명패, 이름 축소 |
| Dot | 멂 | 점만. 이름 없음 |

단계 경계가 되는 거리값은 **눈으로 맞춘다.** 375px에서 이름이 겹치기 시작하는 지점이 곧 경계이므로, 미리 숫자를 정해두는 것이 의미가 없다.

여기에 규칙 하나를 더한다. **사람이 선택되면, 그 사람이 속한 성운의 사람들만 Full로 올리고 나머지는 한 단계씩 내린다.** dim 처리와 같은 동작이라 별도 개념이 늘지 않는다.

같은 역할 안에서도 사람들을 성운 부피 **안쪽에 3차원으로 흩는다.** 같은 깊이에 나란히 세우면 그 순간 리스트가 된다.

## 8. 거리 규칙을 타입으로 잠근다

브리프 9절이 `六合=가까이 / 沖=멀리`, `가까움=좋은 관계`를 금지한다. 이건 주석으로 부탁할 게 아니라 **함수가 애초에 `feature`를 못 받게** 만든다.

```ts
// feature 인자가 없다. 위치가 궁합에 영향받는 코드는 작성 자체가 불가능하다.
function positionFor(role: RelationRole, indexInRole: number): Vector3;
```

`_lib/layout.test.ts`에 테스트 하나만 붙인다 — **같은 역할·같은 인덱스면 `feature`가 무엇이든 좌표가 동일한지.** 시각적인 것은 테스트하지 않는다. 어기면 안 되는 규칙 하나만 잠근다.

## 9. 인터랙션

### 선택

```
사람 탭
  → 나머지 dim (마커 opacity ↓, 성운 밝기 ↓)
  → 나 ↔ 선택자 관계 효과 표시
  → 카메라가 선택자를 화면 상단 1/3에 오도록 보간 이동
  → 바텀시트 상승
```

카메라가 선택자를 **상단 1/3**에 두는 게 중요하다. 화면 중앙에 두면 바텀시트가 정확히 그 사람을 가린다.

해제는 배경 탭 또는 시트 닫기. 카메라는 기본 뷰로 복귀한다.

### 시트가 3D와 싸우지 않게

시트 높이를 **`40vh`로 묶는다.** 3D가 위쪽 60%를 유지한다. 브리프 10절의 명시적 체크 항목이라 처음부터 이 비율로 간다.

내용은 브리프 7절 그대로 — 이름 / 장면명 / 역할 / (feature 있으면) 배지 / 짧은 관계 설명. DS 스타일(흰 카드, `radius-card-lg`, `shadow-elevated`)을 그대로 쓴다.

데스크톱(`md` 이상)은 우측 사이드패널로 바뀐다. 브리프대로 최소 대응만 한다.

### 六合과 沖 — 좋고 나쁨으로 보이면 실패다

**둘은 같은 색, 같은 밝기다.** 오직 움직임의 질로만 다르다.

| Feature | 표현 |
| --- | --- |
| 六合 | 곡선(quadratic bezier)을 따라 입자가 **느리고 연속적으로** 흐른다 |
| 沖 | 두 줄기가 **엇갈리며 미세하게 떤다.** 진폭은 작게 |
| 없음 | 조용한 선 하나. **배지도 라벨도 없다** |

브리프 8절이 "Feature가 없으면 `중립`이라는 별도 표현을 만들지 않는다"고 했다. 그래서 없음은 UI에서 아무 이름도 갖지 않는다.

## 10. 카메라 A/B/C

`OrbitControls` 제한값 세트 3개와 화면 구석의 토글. 토글은 기존 `src/components/SegmentedControl.tsx`를 그대로 재사용한다 (제네릭이라 수정 불필요).

| | polar | azimuth | zoom | pan |
| --- | --- | --- | --- | --- |
| A 제한적 | 60~85° | ±35° | 0.8~1.2x | ✗ |
| B 중간 | 35~100° | 무제한 | 0.6~1.6x | ✗ |
| C 자유+Reset | 15~140° | 무제한 | 0.4~2.5x | 소폭 |

공통으로 지면 아래 관통과 화면 뒤집힘은 전부 금지하고, damping을 켠다. C에만 Reset 버튼이 붙는다.

초기 진입은 **가장 보기 좋은 전체 월드 뷰** 고정이다. 모드를 바꿔도 초기 뷰는 같아야 세 모드를 같은 조건에서 비교할 수 있다.

## 11. 판단 기준

스파이크가 끝나면 375px 실기기에서 이걸 확인한다. **화면에는 표시하지 않는다.**

- 친구 20명이 구분되는가 (LOD가 실제로 먹히는가)
- 이름을 읽을 수 있는가
- 터치하기 쉬운가
- 사람을 선택했을 때 무엇이 일어났는지 바로 이해되는가
- 바텀시트와 3D가 서로 싸우지 않는가
- 카메라가 귀찮지 않은가 — A / B / C 중 어느 것인가
- **차트의 3D 버전처럼 보이지 않는가**

그리고 가장 중요한 하나.

> **"이 화면을 처음 봤을 때 2D 관계 차트보다 확실히 더 매력적이고 기억에 남는가?"**

아니라면 R3F를 고집하지 않는다. 이 문서와 `/lab/relationship-world` 디렉터리를 통째로 지우는 것이 정상적인 결말 중 하나다.
