## 1. 출발점

23장짜리 기획서 한 통. 읽고 먼저 물은 것은 네 가지였고, 답이 서비스의 골격을 정했다.

| 질문 | 답 |
| --- | --- |
| 리포트의 한 섹션인가, 별도 서비스인가 | **별도 서비스**. 궁합·상담과 나란히 |
| 과금 단위는 | **이용권 1장 + 기간별 권한** |
| 상품의 기간 경계는 | 처음엔 "세운 ∩ 대운 전환점" → 나중에 **세운 단독**으로 정정 |
| 범위는 | **8개 섹션 전부 + §22 연결 CTA**. §14 근거 패널은 제외 |

기존 리포트의 `yearlyLuck`(연 12줄)·`daeunOutlook`은 다른 브랜치에서 리포트에서 제거된다.
흐름은 그 빈자리를 메우는 섹션이 아니라, 제거된 이유(명리 단위의 나열)를 반복하지 않는
독립 상품이다.

## 2. 뒤집은 결정 두 개

### 2.1 리포트에 넣는다 → 완전히 분리한다

내가 처음 낸 안은 리포트와 흐름이 프롬프트·저장소·섹션 레지스트리를 공유하도록 공통
기계를 뽑아내는 것이었다(approach B). 이 지적으로 폐기됐다.

> "아니 리포트에 들어가는 게 아니라 궁합, 리포트 처럼 아예 다른 서비스로 따로 분리하는거야"

이 레포의 관행은 **공유가 아니라 전면 복제**다. 궁합이 이미 그렇게 서 있다. 공통 기계를
뽑으면 리포트·궁합·흐름 셋이 한 파일에 묶여, 흐름의 프롬프트를 한 줄 고칠 때마다 이미
팔린 리포트·궁합의 회귀를 걱정해야 한다. 중복을 감수하고 결합을 끊는 쪽을 골랐다.

**결과**: 흐름은 자기 라우트(`/flow`), 자기 테이블(`flows`/`flow_sections`), 자기 레지스트리,
자기 시스템 프롬프트를 가진다. 리포트·궁합 코드는 한 줄도 건드리지 않았다.

### 2.2 세운 ∩ 대운 전환점 → 세운 단독

처음 고른 경계는 "세운과 대운 전환점의 교집합"이었다. 나중에 **입춘 단독**(입춘 → 입춘)으로
정정됐다.

이유는 과금이다. 상품 단위가 명리 연도 1개인데 경계가 대운에도 걸리면, 대운이 바뀌는 해에만
기간이 쪼개져 "이용권 1장 = 1년"이라는 약속이 그 해에만 깨진다. 대운 전환은 **경계가 아니라
07 섹션(`ahead`)의 내용**으로 내려갔다.

## 3. 검토 후 버린 대안

### 3.1 "연 단위 서술 하나" (a안)

구간을 나누지 말고 1년을 한 덩어리로 서술하자는 안. 결제 구조에는 맞았지만 이 판단으로
탈락했다.

> "(a)는 결제 구조에는 맞지만 서비스의 핵심 질문을 약하게 만듭니다 … 이는 표현의 재해석
> 수준이 아니라 **제품 질문의 변경**에 가깝습니다."

서비스가 답하려는 질문은 "올해가 어떤 해인가"가 아니라 **"나는 지금 어떤 시기를 지나고
있는가"**다. 연 단위 서술은 두 번째 질문에 답하지 못한다.

**대신 채택한 것**: 구매 시점에 그 해의 **1~3개 구간 서술을 전부 생성해 박제**하고,
재조회 때는 읽는 시점이 속한 구간을 고르기만 한다. LLM 재호출은 없다.

### 3.2 리포트 본문을 프롬프트 입력으로 넘기기

"타고난 나 × 현재 흐름"이니 리포트 본문을 입력으로 주면 곱이 정확해질 것 같았다. 버렸다.

- 리포트를 안 산 사람은 흐름을 살 수 없게 된다 — 상품 간 의존이 생긴다.
- 리포트를 재생성하면 이미 판 흐름의 전제가 뒤에서 바뀐다.

**대신**: 흐름은 원국을 **자기가 다시 계산**한다. 리포트 텍스트는 입력에 없다.

### 3.3 "중복 방지 = 같은 문장 안 쓰기"

처음엔 리포트와 문장이 겹치지 않게 하는 규칙으로 생각했다. 이렇게 재정의됐다.

> 중복 방지는 문장 중복이 아니라 **역할 중복 방지**다.

리포트는 "당신은 이런 사람"을, 흐름은 "그 사람이 지금 어떤 바람 속에 있는가"를 맡는다.
같은 단어가 나오는 건 문제가 아니다. 흐름이 성향 설명을 시작하는 게 문제다.

### 3.4 "숫자를 일절 넘기지 않는다"

내가 쓴 프롬프트 규칙이 너무 넓었다. 좁혀졌다: 금지 대상은 **점수·확률 같은 내부 계산값**이지
날짜나 나이가 아니다. 날짜는 화면이 붙이고, 점수는 범주 라벨로 바꿔 넘긴다.

## 4. 논의에서 못 박은 설계 원칙

구현 중에 흔들릴 뻔한 것들이라 근거를 남긴다.

### 4.1 `flow_sections` 는 캐시가 아니라 박제다

이용권 1장이 이미 차감된 결과물이다. 값이 없다고 조용히 다시 생성하면 안 판 상품을 공짜로
주거나, 판 상품을 몰래 바꾸는 것이 된다. `period_start/end` 와 `segments` 를 굳이 저장하는
이유도 같다 — 절기 계산이 나중에 정밀해져 입춘 시각이 움직여도 **이미 판 상품의 경계는
소급해서 바뀌면 안 된다**.

특히 `FLOW_SEGMENT_THRESHOLD` 를 한 번 튜닝하면, 저장하지 않았을 경우 11월 서술이 2월 칸에
붙는다.

### 4.2 행 생성은 공짜, 렌더가 유료

`POST /api/flows` 는 행만 만들고 아무것도 차감하지 않는다. 이용권은 **생성기 래퍼 안에서**
차감된다. `produceFlowSections` 는 섹션이 비어 있을 때만 생성기까지 내려가므로, 재조회는
자연히 무료가 된다.

### 4.3 권한은 로직이 아니라 구성으로 얻는다

```
flows_unique (profile_id, flow_year)
  → entitlements.subject_key = flow_id
  → entitlements_unique
```

새 권한 로직을 한 줄도 안 쓰고 "프로필 × 명리 연도당 1회"가 나온다.

### 4.4 게이트가 바깥, 과금이 안쪽

```
gateFlowGeneration(chargeFlowGeneration(inner))   ← 맞음
chargeFlowGeneration(gateFlowGeneration(inner))   ← 틀림. 429 인데 이용권이 빠진다
```

순서가 곧 계약이다. 계획서에 이 순서가 거꾸로 적혀 있었고 구현 중에 뒤집었다.

### 4.5 `solarTermJD` 는 건드리지 않는다

이 함수에는 `+ 9/24`(KST 벽시계)가 박혀 있고, `computeDaeun` 이 그 오프셋이 `birthJD` 와
상쇄되는 데 의존한다. 고치면 이미 판 리포트의 대운이 전부 움직인다. **새 함수
`solarTermInstant` 를 옆에 세웠다.**

### 4.6 전환점은 두 축으로 재고, 십성은 뺀다

- `support` — 용신/희신 대 기신
- `friction` — 지지 관계 가중합 (충·형·해·파·원진·육합 + 삼합/반합)

둘 다 같은 자로 정규화한다. **십성은 탐지에서 의도적으로 뺐다** — 프롬프트의 표현 재료로만
쓴다. 십성까지 점수에 넣으면 무엇이 전환을 만들었는지 사후에 설명할 수 없어진다.

전환은 **인접한 달의 차이(Δ)** 로 잡는다. 점수가 높은 달이 아니다. "요즘 달라졌다"는 감각은
절대값이 아니라 변화에서 온다.

### 4.7 구간 수 `n` 은 스키마 공장으로 강제한다

LLM이 구간 수를 안 지키는 문제는 프롬프트로 부탁하지 않고 타입으로 막았다.

```ts
schema: (n) => z.ZodType     // .length(n) + z.enum(SEGMENT_IDS.slice(0, n)) + 유일성 superRefine
```

길이 `n` + 값의 정의역 `n` + 중복 금지 = 비둘기집 원리로 전단사가 보장된다.

### 4.8 시각은 절대 시각으로

경계를 KST 고정으로 두지 않는다. `flowYearAt(at: Date)` 가 절대 시각을 받는다.

## 8. 아직 안 고친 것

전체 브랜치 최종 리뷰에서 나온 것 중 **고쳐야 하는 것 셋**:

1. **`prompt/facts.ts` 의 숫자 필터가 사실 네 줄을 날린다** — 오행 분포, 십성 분포, 세력
   점수, 신강약. LLM이 **신강/신약을 모른 채** 팔리는 리포트를 전부 쓰고 있다. 결과가
   박제라 판매가 늘수록 비용이 커진다. 필터 대신 신강약은 단계 어휘로, 오행·십성은
   많음/적음/없음 라벨로 넘겨야 한다.
2. **`/flow` 에 프로필을 바꿀 방법이 없다** — 승인된 스펙에 있던 `[다른 프로필 선택]` 을
   내가 계획으로 옮기며 빠뜨렸고, 그래서 18개 태스크 리뷰가 전부 이걸 못 봤다. 기본
   프로필이 가족인 사용자는 자기 것을 못 산다. `no_profile` 도 막다른 길이다.
3. **죽은 export 셋** — `FlowSectionWrite`, `listFlows`(이걸 위한 마이그레이션 `0035` 포함),
   `monthTermAt`.

기록만 하고 넘긴 것: 게이트 순서 불변식이 실제 조립 지점에서 테스트되지 않음 /
`WEIGHT_TOTAL` 이 시지를 가정하는데 시간 미상 프로필에는 없음(임계값도 `hour: 9` 로만 보정)
/ 오류 화면에 `h1` 없음 / 요금제한 화면 둘의 문구 불일치 / 프롬프트에서 "구간"이 두 뜻으로

## 10. 구현 중 리뷰가 잡은 것들

계획서에 내가 써 둔 코드에서 실제 버그 8건이 나왔다. 유형만 남긴다.

- 테스트 픽스처에 `as const` 누락 — vitest는 통과, typecheck가 잡음.
- **같은 정밀도 불일치가 세 곳에서 재발** — 대운 시작 나이를 반올림값으로 쓴 곳과
  정밀값으로 쓴 곳. 1967년생에서 실제로 갑술/을해가 갈렸다. `currentDaeun` 하나만 답하도록
  통일해서 닫았다.
- Neon의 jsonb가 파싱된 채로 올 때와 문자열로 올 때가 있다 — 둘 다 받고, 형태가 깨졌으면
  **던진다**(상담 코드의 `[]` 로 강등하는 처리와 일부러 다르게).
- 오름차순 배열에 `.find(p => p.startAge <= age)` — 유년기 대운이 나온다.
- `produceFlowSections` 가 `stored: true` 를 무조건 반환 — 궁합의 계약에 맞추기로 정리.
- 게이트/과금 합성 순서가 거꾸로 (4.4).

교훈 하나: **리뷰가 근거로 든 테스트를 실제로 열어 확인해야 한다.** 한 번은 구현자의 반박이
그럴듯했는데 인용한 테스트가 그 주장을 뒷받침하지 않았다.
