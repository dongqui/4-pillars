# Project Saju — 관계 엔진 & 관계 세계 최종 정리

> 상태: **현재 논의 기준 최종 결정안**  
> 목적: 관계 엔진, 사용자 분류, 3D 관계 세계, v1 구현 범위를 하나의 기준 문서로 정리한다.

---

## 0. 프로젝트 원칙

> **엔진은 넓게 설계하고, 사용자에게는 단순하게 보여주고, 3D는 싸게 실험한다.**

관계 엔진과 렌더링은 분리한다.

- 관계 엔진은 Babylon.js / SVG / CSS 등에 종속되지 않는다.
- v1에서 3D는 필수 정보 표현 수단이 아니라 **연출과 차별화 가능성을 검증하는 실험**이다.
- 장기적으로 관계 피처가 늘어날 경우 3D는 공간·빛·선·움직임·환경으로 정보를 분산하는 그릇이 될 수 있다.
- 3D가 기대만큼 좋지 않으면 2.5D/SVG로 즉시 철수한다.

---

# 1. 최종 관계 엔진 구조

기존의:

```text
5 역할 × 3 작용 = 15 Archetype
```

구조는 **폐기한다.**

최종 구조는 다음과 같다.

```text
10 Ten-God Subtype
        ↓ derived
5 Core Relationship Role
        +
Relationship Features[]
        +
60 × 60 Pair Identity
        +
향후 전체 사주 관계 레이어
```

핵심 구분:

> **Core Role = 이 사람은 나에게 무엇인가**  
> **Feature = 우리 사이에서 어떤 현상이 발생하는가**

이 둘은 서로 다른 종류의 축이다.

---

# 2. 5 Core Relationship Role

일간 기준 십성 관계를 사용자 언어로 번역한 상위 분류다.

| 명리 그룹 | 사용자 표현 | 핵심 의미 |
|---|---|---|
| 인성 | 나를 채워주는 사람 | 받아들이고 배우게 함 |
| 비겁 | 나란히 서는 사람 | 나와 상대의 위치·정체성을 드러냄 |
| 식상 | 나를 표현하게 하는 사람 | 말·행동·창작을 밖으로 꺼내게 함 |
| 재성 | 나를 움직이게 하는 사람 | 현실적인 행동·계획·결과로 움직이게 함 |
| 관성 | 나를 다듬는 사람 | 기준·책임·경계·질서를 의식하게 함 |

이 5개는:

- 모든 Pair에 항상 하나 존재하고
- 관계 세계의 가장 안정적인 상위 구조이며
- 3D/2D 모두에서 위치 또는 지역의 기준으로 사용한다.

---

# 3. 10 Ten-God Subtype

5개 Core Role의 세부 형태다.

```text
비겁 → 비견 / 겁재
식상 → 식신 / 상관
재성 → 정재 / 편재
관성 → 정관 / 편관
인성 → 정인 / 편인
```

저장 시에는 `role`과 `subtype`을 둘 다 source of truth로 두지 않는다.

권장:

```text
tenGod 저장
→ role은 tenGod에서 파생
```

예:

```ts
function getRoleFromTenGod(tenGod: TenGod): RelationshipRole {
  // 비견/겁재 → 비겁
  // 식신/상관 → 식상
  // ...
}
```

이렇게 하면 `role`과 `subtype`의 불일치 가능성을 없앨 수 있다.

# 4. Relationship Features

Relationship Feature는 관계의 본체가 아니라 **선택적으로 발생하는 작용**이다.

중요한 구조적 원칙:

```text
Core Role
= 항상 정확히 1개

Relationship Feature
= 0개 ~ 여러 개
```

따라서 둘을 곱해 고정 격자를 만드는 방식은 사용하지 않는다.

## v1 구현

v1에서는 우선:

```text
六合
沖
```

만 계산한다.

아무것도 검출되지 않았다고 해서 이를 별도의 “중립 관계”로 부르지 않는다.

정확한 의미는:

> **현재 검사한 Relationship Feature가 없는 상태**

다.

## 향후 확장 후보

```text
刑
破
害
원진
三合
方合
천간 관계
오행 보완
연·월·시주 관계
전체 사주 상호작용
```

등을 추가할 수 있다.

한 Pair에 여러 작용이 동시에 존재할 수 있으므로 `features[]` 배열 구조를 사용한다.

# 5. 왜 15 Archetype을 폐기하는가

처음에는:

```text
5 Role × (合 / 중립 / 沖)
= 15 Relationship Archetype
```

을 생각했다.

15개의 메커니즘 자체는 의미적으로 구분할 수 있었다.

그러나 구조적으로 문제가 있다.

## 문제 1 — 축의 성격이 다름

Role은 모든 Pair에 반드시 하나 존재한다.

반면 합·충은:

- 없을 수도 있고
- 하나 있을 수도 있고
- 향후 여러 관계 작용이 동시에 붙을 수도 있다.

즉:

> **필수 단일 축과 선택적 다중 이벤트를 곱해서 하나의 격자로 만든 것**

자체가 잘못된 모델링이었다.

## 문제 2 — 실제 분포도 크게 치우침

육합과 충만 볼 경우 상대방의 12지지 중:

```text
六合 = 1
沖   = 1
나머지 = 10
```

이므로 60×60 = 3,600 Pair를 단순 분류하면 대략:

```text
六合      300  ≈ 8.33%
沖        300  ≈ 8.33%
무표식  3,000 ≈ 83.33%
```

이 된다.

다만 **이 분포는 폐기의 핵심 이유가 아니라 구조적 오류가 드러난 증상**으로 본다.

향후 형·파·해를 추가해 무표식 비율이 줄어들더라도 15 격자로 돌아가지 않는다.

---

# 6. 기존 15개 메커니즘 문장의 처리

15 Archetype은 폐기하지만, 15칸에서 작성한 관계 설명은 버리지 않는다.

역할을 다음과 같이 변경한다.

```text
❌ 15개의 상위 Relationship Type

⭕ Role × Feature 조합별 설명 카피
```

예:

## 인성 기본

> 나를 채워주는 사람

## 인성 + 六合

> 상대의 조언·돌봄·관점이 내 안으로 자연스럽게 들어오는 관계.

## 인성 + 沖

> 상대의 관점이 내 익숙한 생각을 흔들고 다시 생각하게 만드는 관계.

같은 방식으로 각 Role에 Feature가 붙었을 때 설명을 확장한다.

물안개 속 들꽃 · 乙亥

처럼 보여줄 수 있다.

```text

```

같은 전문용어를 기본 노출하지 않는다.

최종 네이밍은 별도 작업으로 확정한다.

# 8. 유료 Pair 해석

동적 Pair 타이틀과 긴 해석은 무료 v1보다 **유료 궁합**에 더 적합하다.

무료:

> **우리는 어떤 구조의 관계인가?**

유료:

> **왜 우리 관계가 이렇게 작동하는가?**

예:

무료:

```text
나란히 서는 사람
[자연스럽게 맞물리는 관계]
```

유료:

```text
같은 편이 되기 쉬우면서도,
서로의 위치를 계속 확인하게 되는 관계
```

유료 단계에서는:

- subtype
- Relationship Features
- 60×60 Pair
- 향후 연·월·시주
- 전체 사주 상호작용

을 더 깊게 조합한다.

# 9. 60 × 60 Pair

각 사람은 60일주 중 하나를 가진다.

따라서 방향성 있는 일주 Pair는:

```text
60 × 60 = 3,600
```

개다.

중요:

```text
A → B ≠ B → A
```

가 될 수 있다.

따라서 Pair는 정렬하지 않는다.

예:

```text
甲子>壬辰
```

과

```text
壬辰>甲子
```

는 서로 다른 Pair다.

## Pair의 의미

3,600개의 고정 문구를 수작업으로 작성하는 것이 아니다.

관계 결과는:

```text
Ten-God Subtype
+
Derived Core Role
+
Relationship Features[]
+
A의 60일주 캐릭터
+
B의 60일주 캐릭터
```

를 조합해 생성한다.

---

# 10. 데이터 모델

권장 기본 형태:

```ts
type Relationship = {
  sourceCharacter: SajuCharacter;
  targetCharacter: SajuCharacter;

  tenGod: TenGod;

  features: RelationshipFeature[];

  pairKey: `${Sexagenary}>${Sexagenary}`;
};
```

Core Role은 저장하지 않고 파생한다.

```ts
const role = getRoleFromTenGod(relationship.tenGod);
```

## v1 RelationshipFeature

현재 계산하지 않는 미래 규칙까지 미리 구현하지 않는다.

v1에서는:

```ts
type RelationshipFeature =
  | {
      type: "branch_relation";
      value: "六合" | "沖";
    };
```

정도로 시작한다.

핵심은:

> **현재 계산은 좁게, 저장 구조는 여러 feature를 받을 수 있게.**

향후 실제 규칙을 구현할 때 union을 확장한다.

# 11. B07 스코프

기존 B07이:

```text
5분류 + 육합·충 배지
```

수준이었다면, 다음 요구를 추가한다.

- 관계는 방향성이 있음
- `source → target` 구조를 명시
- `features[]` 확장형 데이터 구조 사용
- `tenGod`을 source of truth로 두고 Role은 derived
- `pairKey`에 방향성을 포함
- v1 계산은 六合 / 沖만 구현
- 미래 feature 계산은 구현하지 않음

스키마 설계가 추가되므로 기존 size:S였다면 **M으로 상향**하는 것이 타당하다.

# 12. 관계 세계의 최종 공간 구조

기존 아이디어:

```text
5개 역할 × 3개 장소
= 15개의 공간
```

은 폐기한다.

새 구조:

```text
5개의 관계 세계
= Core Role

각 사람
= 60일주 카드 / Standee

Relationship Features
= 공간에서 발생하는 현상
```

즉 사람의 위치는 기본적으로 **그 사람이 나에게 어떤 역할인가**를 보여준다.

합·충·형·파·해 등은 위치를 또 쪼개는 대신 **현상으로 표현**한다.

# 13. 3D 표현 원칙

## 5개의 세계

예:

- 나를 채워주는 세계
- 나란히 서는 세계
- 나를 표현하게 하는 세계
- 나를 움직이게 하는 세계
- 나를 다듬는 세계

정확한 Art Direction은 별도 단계에서 정한다.

## Relationship Features의 표현

예시:

```text
六合
→ 자연스럽게 이어지는 길
→ 부드러운 빛
→ 연결되는 흐름

沖
→ 팽팽한 에너지
→ 흔들림
→ 서로 다른 힘이 부딪히는 현상

刑
→ 반복 / 압박 / 꼬이는 패턴

破
→ 깨짐 / 균열 / 끊어짐

害
→ 엇갈리는 흐름

三合
→ 여러 노드가 하나의 구조 또는 흐름을 형성
```

이는 아직 시각 언어 후보이며, 명리 규칙 자체와 동일시하지 않는다.

# 14. 3D에서 금지하는 표현

다음 의미 연결은 사용하지 않는다.

```text
합 = 가까움 = 친함 = 좋은 관계
충 = 멀어짐 = 나쁨
```

따라서:

> **거리 = 관계의 좋고 나쁨**

으로 사용하지 않는다.

이 원칙은 Babylon 전용이 아니라 **렌더러 독립적인 제품 원칙**이다.

형태로 사용하는 안을 우선한다.

60종 일러스트는 추후 별도 IP/브랜드 결정이 있을 때만 착수한다.

# 17. Babylon.js의 역할

Babylon.js를 쓰는 이유를 명확히 구분한다.

## v1에서

3D는:

> **정보량 때문에 필수인 것이 아니라 기억에 남는 UX와 공유하고 싶은 경험을 만들 수 있는지 검증하는 연출 수단**

이다.

## 장기적으로

Relationship Feature가 늘어나면:

- 공간
- 지형
- 높이
- 빛
- 선
- 움직임
- 환경 변화

등 여러 표현 변수를 활용할 수 있으므로 **복잡한 관계 정보를 분산하는 그릇**이 될 가능성이 있다.

---

# 18. 폐기한 Babylon 방향

다음 구조는 사용하지 않는다.

```text
중앙의 나
+
동심원 3개
+
5개 방사형 섹터
+
구체 노드
+
항상 보이는 연결선
```

이유:

- 기존 원형 관계 차트의 3D 버전처럼 보임
- 시각적으로 디버그/데이터 차트 느낌이 강함
- 합=가까움, 충=멀어짐으로 오독될 수 있음
- 3D를 쓰는 이유가 약해짐

---

# 19. 다음 Babylon 스파이크

다음 실험은:

```text
중앙에 나

주변에 5개의 관계 세계

각 세계 안에 친구 카드/Standee

평소 연결선 최소화

친구 선택
→ 다른 친구 Dim
→ 나와 상대 사이 Feature 현상 활성화
→ 카메라 Focus
→ HTML 관계 카드 표시
```

구조로 테스트한다.

역할 분리:

```text
Babylon
= 공간 / 지형 / 빛 / 움직임 / 관계 현상

React / HTML
= 이름 / 카드 / 설명 / 검색 / 필터 / CTA
```

원칙:

> **Babylon은 관계를 느끼게 하고, HTML은 관계를 이해하게 한다.**

# 20. Babylon 스파이크 성공 기준

스파이크가 끝없이 커지는 것을 막기 위해 통과 기준을 사전에 둔다.

## UX

- 375px 모바일에서 친구 5~10명이 구분됨
- 원하는 친구를 최대 2탭 안에 선택 가능
- 선택 → 관계 카드 연결이 자연스러움
- 별도 튜토리얼 없이 기본 조작을 이해할 수 있음
- 카메라 조작이 스트레스를 유발하지 않음

## 성능

- 중저가 모바일에서도 지속적인 심한 프레임 저하가 없음
- 친구 20~30명까지 장면이 무너지지 않음
- 선택 애니메이션에서 눈에 띄는 hitch가 없음
- asset 용량을 합리적인 수준으로 제한 가능

## 개발 비용

- 핵심 장면을 1~2일 스파이크 범위에서 구현 가능
- React/Babylon 상태를 과도하게 이중 관리하지 않아도 됨
- 모바일 대응이 별도 제품 개발 수준으로 커지면 탈락

## 핵심 정성 기준

> **동일 기능의 2D 버전보다 명백히 더 기억에 남는가?**

“조금 더 예쁘다” 정도면 Babylon을 채택하지 않는다.

# 23. 현재 확정 / 보류 / 폐기

## 확정

- 5 Core Relationship Role
- 10 Ten-God Subtype
- Role은 TenGod에서 derived
- Relationship Features[]
- A→B 방향성

- 2D/3D 모두 거리=좋고 나쁨 금지
- 60종 일러스트를 필수 dependency로 두지 않음
- 무료 = 역할 + Feature
- 유료 = Pair의 깊은 이유
- 15 Archetype은 폐기

- 유료 전체 사주 궁합 계산 규칙

- 합=가까움 / 충=멀어짐

# 최종 한 줄 정의

> **Project Saju의 관계 시스템은 5개의 관계 역할을 골격으로 삼고, 10십성과 여러 Relationship Feature, 60×60 Pair의 개성을 겹쳐 각 관계를 설명한다. 3D 관계 세계에서는 역할을 공간으로, Feature를 현상으로 표현한다.**
