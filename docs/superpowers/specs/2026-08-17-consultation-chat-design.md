# 고민상담 (채팅) 설계

2026-08-17

리포트는 한 번 쓰고 끝나는 글이다. 고민상담은 사용자가 자기 말로 물어보고 사주를 아는
상대가 답하는 왕복이다. 리포트가 못 하는 일 — "그래서 제 경우엔 어떡하죠?" — 을 받는
자리이고, 이용권을 쓰게 만드는 첫 유료 동선이다.

## 결정 사항 요약

| 항목 | 결정 |
| --- | --- |
| 상담 상대 | 고정 상담사 1명 (페르소나 하나) |
| 이용권 소모 단위 | 상담 1건 = 이용권 1장 |
| 상담 1건의 크기 | 사용자 발화 10회 |
| 무료 체험 | 없음 |
| 상담 근거 | `chartFacts` (기존 리포트 파이프라인의 [사실] 블록) |
| 응답 형태 | 말풍선 배열 + 추천질문 2개, tool 스키마로 강제 |
| 모델 | `deepseek-v4-pro` (`CONSULT_MODEL` 상수로 분리) |
| 이용권 시스템 | **범위 밖.** 타입만 선언하고 구현은 나중에 배선 |

이용권 가격(1장 1,000원)과 구매 흐름은 다른 세션에서 진행 중이다. 이 문서는 고민상담
기능 자체만 다루고, 이용권은 경계 너머의 계약(`TicketPort`)으로만 등장한다.

## 1. 데이터 모델

```sql
-- migrations/0012_consultations.sql

-- 상담 1건 = 이용권 1장 = 이 테이블 한 행.
CREATE TABLE IF NOT EXISTS consultations (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id      bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  profile_id   bigint REFERENCES profiles(id) ON DELETE SET NULL,
  status       text NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'closed')),
  turns_used   int  NOT NULL DEFAULT 0,
  turn_limit   int  NOT NULL DEFAULT 10,
  title        text,
  tokens_in    bigint NOT NULL DEFAULT 0,
  tokens_out   bigint NOT NULL DEFAULT 0,
  created_at   timestamptz NOT NULL DEFAULT now(),
  closed_at    timestamptz
);

CREATE INDEX IF NOT EXISTS consultations_user_idx
  ON consultations (user_id, created_at DESC);

CREATE TABLE IF NOT EXISTS consultation_messages (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  consultation_id bigint NOT NULL REFERENCES consultations(id) ON DELETE CASCADE,
  role            text NOT NULL CHECK (role IN ('user', 'counselor')),
  bubbles         jsonb NOT NULL,
  suggestions     jsonb,
  turn_no         int NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS consultation_messages_thread_idx
  ON consultation_messages (consultation_id, id);
```

`turn_limit` 을 상수가 아니라 컬럼에 박는 이유는 `purchases.amount` 와 같다. 정책이
나중에 12회로 바뀌어도 이미 팔린 상담은 산 조건 그대로 끝나야 한다.

`profile_id` 는 `ON DELETE SET NULL` 이다. 백로그가 `purchases.profile_id` 의
`CASCADE` 를 문제로 지적한 것과 같은 이유고, 프로필이 지워져도 이미 나눈 대화는
남아야 한다.

`bubbles` 를 `jsonb` 배열로 두는 것은 응답 스키마와 짝이다. LLM 이 말풍선 배열로
답하니 저장도 그 모양 그대로 받고, 화면이 다시 쪼갤 필요가 없다. `role='user'` 인
행은 항상 길이 1 이고 `suggestions` 는 NULL 이다.

`tokens_in` / `tokens_out` 은 §6 의 비용 상한이 가정이 아니라 실측과 맞는지 보기
위한 관측 컬럼이다. 기존 DeepSeek 어댑터의 `onUsage` 훅이 그대로 꽂힌다.

## 2. 상태 전이와 이용권 차감

```
[홈 카드] → /consult
              ├ 비로그인      → /login?next=/consult
              ├ 프로필 없음   → /funnel?step=name
              └ 로그인+프로필 → 상담 목록

[목록] → "새 상담 시작하기" → 첫 고민 입력 → POST /api/consultations
            1. 이용권 잔액 확인          (없으면 402 → 구매 안내)
            2. consultations 행 INSERT   (status='open', turns_used=0)
            3. 이용권 차감               ← 차감 시점
            4. 첫 턴 실행
          → /consult/{id}

[대화 중] → POST /api/consultations/{id}/messages
              turns_used < turn_limit 이면 진행, 아니면 409
              마지막 턴을 마치면 status='closed', closed_at 기록

[종료 후] → 읽기 전용. 이력은 목록에서 계속 볼 수 있다
```

### 차감 시점을 "상담 개설"에 두는 이유

버튼을 누르는 순간이 아니라 **첫 고민을 실제로 써서 보낸 순간**이다. 화면만 열어보고
나간 사람에게 1,000원을 물리지 않으면서, 차감 없이 대화가 시작되는 창도 열지 않는다.

순서가 3 → 4 인 것도 의도적이다. 차감을 LLM 호출 뒤로 미루면 차감 실패 시 이미 답변을
준 뒤라 되돌릴 수 없다. 차감이 먼저면 첫 턴 LLM 실패 시 이용권을 돌려줘야 하는데,
이건 되돌릴 수 있는 방향의 실패다.

되돌리기까지 실패하면 `consultations` 행은 `turns_used = 0` 으로 남는다. 그 행이 곧
증거이므로 별도 보상 로직을 두지 않고, **`turns_used = 0` 인 상담은 이용권을 다시
쓰지 않고 재개할 수 있게** 한다. 사용자는 그냥 다시 물어보면 되고, 이미 낸 돈은 살아
있다.

### 이용권 모듈과의 경계

```ts
// src/lib/consultations/ticket-port.ts — 타입만. 구현은 다른 세션 것을 배선한다.
export interface TicketPort {
  getBalance(userId: string): Promise<number>;
  /** 잔액이 부족하면 throw. consultationId 는 멱등키 자리다 */
  spend(userId: string, consultationId: string): Promise<void>;
  refund(userId: string, consultationId: string): Promise<void>;
}
```

이 파일 하나가 다른 세션과의 유일한 접점이다. 이용권 작업이 끝나면 stub 만 실구현
import 로 갈아 끼운다.

스텁의 동작은 갈린다. `spend` / `refund` 는 **던진다** — 배선 전에 상담이 공짜로
열리면 안 되고, 던져야 그 사실이 즉시 드러난다. `getBalance` 는 0 을 돌려준다 —
던지면 목록 화면 전체가 500 이 되어 개발 중에 아무것도 못 본다. 대신 그 0 을 화면에
숫자로 표시하지는 않는다 (§4-b). 라우트는 이 인터페이스만
알고 구현을 모른다 — 테스트에서도 같은 자리에 가짜를 넣는다.

`consultationId` 를 넘기는 것은 멱등키 자리를 지금 열어 두기 위해서다. 다른 세션이
어떻게 구현하든 같은 상담에 두 번 차감되지 않게 할 손잡이가 필요하다.

## 3. 프롬프트와 응답 스키마

### 메시지 배치 — 캐시 경계가 곧 비용이다

`src/app/api/saju/_lib/prompt/facts.ts` 가 "캐시 경계가 곧 프롬프트 경계다"라고 못
박아 뒀는데, 상담에서는 그게 비용으로 직결된다. 매 턴 바뀌는 값을 앞쪽에 두면 prefix
캐시가 통째로 깨지고 §6 의 8원이 30원이 된다.

```
system     상담사 페르소나 + 규칙          ← 영원히 고정
user       [사실] 블록 (chartFacts)        ← 이 상담 내내 고정
assistant  첫 인사
user/assistant  … 왕복 …                   ← 뒤로만 자란다
user       <이번 발화>
           ---
           남은 턴: 3                       ← 매 턴 바뀌는 값은 맨 끝에만
```

`남은 턴` 을 시스템 프롬프트가 아니라 마지막 user 메시지 꼬리에 붙이는 게 이 배치의
전부다. 앞의 모든 것이 안정적인 prefix 라 캐시에 얹힌다.

이 값을 모델에게 알려주는 이유는 페이스 조절이다. 남은 턴을 모르면 3턴 남았는데 새
주제를 열고 마지막 턴을 "다음에 더 얘기해요"로 끝낸다. 마지막 턴에는 "이번이 마지막
답변이니 정리하고 마무리하라"를 명시적으로 넣는다.

### 응답 스키마

```ts
{
  bubbles:     string[]   // 2~5개, 각 120자 이하
  suggestions: string[]   // 정확히 2개, 각 30자 이하 (마지막 턴에는 0개)
  title?:      string     // 첫 턴에만, 20자 이하
  crisis:      boolean    // 위기 발화로 판단해 안내로 답했는지 (§ 위기 발화)
}
```

`suggestions` 는 화면 하단의 추천 질문 두 개다. 스키마로 강제하면 사용자가 뭘 물어야
할지 몰라 멈추는 지점이 사라진다. 개수를 tool 파라미터 스키마에 박는 것은 기존 세운·
대운의 행 수 강제와 같은 수법이고, 어댑터가 이미 `inputSchema` 를 그대로 실어 보낸다.

`title` 은 목록에 뜰 제목이다(§5). 첫 턴 응답에 얹어 같은 호출 안에서 받으므로 비용이
들지 않고, 사용자 발화 앞 30자를 자르는 것보다 읽을 만한 제목이 나온다
("아 진짜 요즘 회사에서 너무 힘든데 어떻게" → "직장에서의 답답함").

### 규칙 — 리포트에서 가져올 것과 버릴 것

`SYSTEM_PROMPT` 의 여섯 규칙 중 그대로 가져오는 것:

- 사실 블록 밖 정보 금지 (이름·나이·생년월일·직업·가족관계·지역을 지어내지 않는다)
- 단정 금지 ("반드시", "~할 운명이다" 대신 경향으로)
- 길흉 단정 금지
- 사주 용어 금지 — 피벗 정책이라 상담에서도 유지한다. 상담사가 "편관이 강해서"라고
  말하는 순간 톤이 무너진다
- 의료·법률·투자·수명·임신에 대한 확정적 조언 금지

버리는 것: **숫자 금지**. 리포트에서 숫자를 막은 것은 화면이 계산값을 따로 붙이기
때문인데 상담에는 그런 화면이 없다. "사실 블록 밖 정보 금지"가 그 역할을 이어받는다.

새로 넣는 대화체 규칙:

- 말풍선 하나는 한 호흡이다. 이어지는 말풍선이 같은 말을 되풀이하지 않는다
- 반드시 되묻고 끝낸다 (마지막 턴 제외)
- 해요체, 호칭 없음 — 리포트와 동일

### 위기 발화

고민상담은 자해·자살·학대 이야기가 들어오는 표면이다. 리포트는 일방향 생성이라 이
문제가 없었지만 상담은 다르다. 두 겹을 넣는다.

1. 시스템 프롬프트에 명시 — 위기 신호가 보이면 사주 해석으로 답하지 말고, 지금 감정을
   먼저 받아 주고 **자살예방 상담전화 109** 를 안내한다
2. 그 턴은 `turns_used` 에서 차감하지 않는다. 위기 상황에서 "남은 대화 0회"를 만나는
   일은 없어야 한다

2번은 모델이 스키마에 `crisis: boolean` 을 실어 알린다. 프롬프트 한 겹뿐이라 새는
구멍이 있다 — 키워드 필터를 앞단에 더 얹는 것은 이번 범위 밖으로 둔다.

## 4. 화면

### `/consult/[id]` — 대화방

```
┌─────────────────────────────────┐
│ ←  🐈 상담사       남은 대화 7회 │
├─────────────────────────────────┤
│ 🐈 ┌──────────────┐              │
│    │ 말풍선 1     │              │  상담사: 좌측, 회색
│    └──────────────┘              │  400ms 간격 순차 노출
│    ┌──────────────┐              │
│    │ 말풍선 2     │              │
│    └──────────────┘              │
│              ┌──────────────┐    │
│              │ 내 발화      │ 🙂 │  사용자: 우측, accent
│              └──────────────┘    │
├─────────────────────────────────┤
│ [추천 질문 1]    [추천 질문 2]   │  칩 — 누르면 그대로 전송
│ ┌─────────────────────────────┐  │
│ │ 질문을 입력하세요        ↑ │  │  1,000자 상한
│ └─────────────────────────────┘  │
└─────────────────────────────────┘
```

서버 컴포넌트가 이력을 읽어 넘기고, 채팅 UI 만 클라이언트 컴포넌트다.

두 가지가 이 화면의 체감을 결정한다.

**말풍선 순차 노출** — 배열은 한 번에 도착하지만 400ms 간격으로 하나씩 붙인다.
스트리밍을 쓰지 않기로 한 대가를 여기서 갚는다. 배열이 이미 손에 있으니 도중에 끊길
걱정이 없고, 사람이 연달아 말하는 리듬이 난다.

**대기 표시** — pro 모델이라 첫 말풍선까지 5~10초 걸린다. 답이 오기 전까지 상담사
아바타 옆에 점 세 개 애니메이션을 띄운다. 이게 없으면 화면이 죽은 것처럼 보인다.

턴을 다 쓰면 입력창 자리가 "상담이 마무리됐어요"와 새 상담 CTA 로 바뀐다. 지난 대화는
계속 스크롤해 읽을 수 있다. 헤더의 `←` 는 목록으로 돌아간다.

### `/consult` — 목록

```
┌─────────────────────────────────┐
│ 고민상담              이용권 3장 │
├─────────────────────────────────┤
│ ┌─────────────────────────────┐ │
│ │  + 새 상담 시작하기         │ │
│ └─────────────────────────────┘ │
│                                 │
│ 이직을 해야 할지 모르겠어요     │  ← title
│ 지금 자리에서 답답한 게…   7/10 │  ← 마지막 말풍선 · 진행
│ 어제                            │
│ ─────────────────────────────── │
│ 오래 만난 사람과의 관계         │
│ 그 마음이 식은 게 아니라…  완료 │
│ 8월 12일                        │
└─────────────────────────────────┘
```

진행 중인 상담이 위, 끝난 것이 아래. `7/10` 이 있으면 "돌아가면 3번 더 물어볼 수
있다"가 바로 읽힌다. 진행 중 상담이 있어도 자동으로 그리로 보내지 않는다 — 목록이
있으면 자동 리다이렉트는 방해가 된다.

Claude 처럼 사이드바로 두지 않는 이유는 이 서비스가 모바일 우선이기 때문이다.
사이드바는 모바일에서 결국 드로어가 되는데, 상담은 홈 카드에서 들어오는 흐름이라
목록 화면이 한 겹 더 단순하다.

"새 상담 시작하기"를 누르면 "무슨 고민이 있으세요?" 한 줄과 큰 입력창이 뜬다. 상담이
하나도 없으면 목록 대신 "아직 나눈 이야기가 없어요"와 시작 버튼만 둔다.

`?profile=` 는 새 상담을 만들 때 `consultations.profile_id` 로 들어가는 값이다.
기존 `parseProfileParam` 으로 검증하고, 없거나 남의 프로필이면 그 계정의 첫 프로필로
물러선다. 이미 만들어진 상담은 자기 `profile_id` 를 쓰므로 이 파라미터를 보지 않는다.

**헤더 우측의 "이용권 N장" 은 `getBalance` 가 실제로 배선된 뒤에 켠다.** 그전까지는
자리를 비우고, 잔액 부족은 상담 개설이 402 를 돌려줄 때만 드러난다 — 스텁이 돌려주는
0 을 사용자에게 "0장"이라고 보여주면 거짓말이 된다.

### 홈 카드

`ExploreGrid` 의 **두 번째 자리**, 리포트 바로 다음. 궁합은 아직 "준비 중"이라
비활성인데 유료 전환 동선을 비활성 카드 뒤에 두면 안 된다.

```
나에게 묻고 싶을 때
고민상담
```

## 5. 비용 상한

10턴이 이용권 1장(1,000원)을 넘지 않는지 확인한 계산이다.

전제 — 시스템 프롬프트 + `chartFacts` ≈ 1,200토큰(고정 prefix), 사용자 발화 상한
1,000자 ≈ 800토큰, 상담사 답변 말풍선 5개 ≈ 300토큰. **모든 턴이 상한을 꽉 채운다**고
본다. 매 턴 전체 이력을 다시 보내므로 입력이 2차로 자란다.

```
턴 i 입력 = 1,200 + (i-1) × 1,100 + 800
10턴 누적 입력 = 20,000 + 1,100 × 45 = 69,500 토큰
10턴 누적 출력 = 3,000 토큰
```

캐시가 걸리면 매 턴 새로 읽히는 것은 직전 상담사 답변(300) + 이번 발화(800) = 1,100
토큰뿐이고 나머지는 적중이다 (miss = 1,200 + 800 + 9 × 1,100 = 11,900).

| | 캐시 미적중(최악) | 캐시 적중(실제) |
| --- | --- | --- |
| 입력 | 69,500 tok → $0.019 | miss 11,900 + hit 57,600 → $0.005 |
| 출력 | 3,000 tok → $0.0013 | $0.0013 |
| **합** | **약 30원** | **약 9원** |

1,000원 대비 최악 3%, 평상시 0.9%. PG 수수료(약 3.4% = 34원)가 LLM 비용보다 크다.

단가는 입력 $0.28/M(캐시 미스)·출력 $0.42/M 기준으로 잡았다. **DeepSeek V4 실단가는
배선 전에 가격표로 확인한다.** 10배가 틀려도 300원이라 결론은 바뀌지 않는다.

이 계산이 성립하는 것은 상한이 코드로 강제될 때뿐이다. 네 개의 자물쇠를 둔다.

1. **입력 상한** — 사용자 발화 1,000자. 서버에서 zod 로 거부한다 (클라 `maxlength` 는
   편의일 뿐이다)
2. **출력 상한** — 말풍선 스키마에 개수 2~5 + 각 `maxLength`, 그리고 `max_tokens`
3. **턴 상한** — `turn_limit` 컬럼
4. **관측** — `consultations.tokens_in / tokens_out` 누적

4번이 있으면 실측이 가정과 갈리는 순간 바로 보인다.

## 6. 파일 구조

```
src/lib/consultations/

  budget.ts           턴 예산·상태 전이 (순수)

  schema.ts           말풍선/추천질문/제목 tool 스키마 (순수)
  input.ts            발화 검증 — 1,000자 상한 (zod)

```

코어를 `src/app/api/.../_lib` 이 아니라 `src/lib/consultations/` 에 두는 이유는
백로그 §6 이 지적한 문제를 반복하지 않기 위해서다 — `api/saju/_lib` 이 두 진입점의
공용 코어가 되면서 소유권이 흐려졌다. 상담도 라우트와 페이지 양쪽에서 쓰이므로
처음부터 `src/lib` 에 둔다.

재사용하는 것은 `chartFacts`(사실 블록)와 `createDeepSeekTransport`(어댑터) 두 개다.
기존 섹션 파이프라인 자체는 쓰지 않는다 — 그쪽은 *원국 단위 캐시 + 1회성 생성*이
전제라 유저별 대화 이력과 캐시 키부터 충돌한다.

## 7. 테스트

순수 모듈에 단위 테스트를 단다.

- `budget` — 턴 소진, `open → closed` 전이, 한도 초과 거부, 위기 턴 미차감,
  `turns_used = 0` 재개
- `prompt` — 캐시 경계. 매 턴 바뀌는 값(남은 턴)이 prefix 에 새지 않는지, 마지막
  턴 지시문이 붙는지
- `schema` — 말풍선 2~5개·추천질문 정확히 2개 강제, 마지막 턴 0개
- `input` — 1,000자 초과 거부, 빈 발화 거부
- `store` — 행 매핑 (`bubbles` jsonb ↔ `string[]`)

라우트는 기존 관례대로 핸들러를 순수 함수로 뽑아 `TicketPort` 와 transport 를 주입해
테스트한다. 차감 실패·LLM 실패의 되돌리기 경로가 여기 걸린다.

리포에 `*.test.tsx` 가 하나도 없으므로(서버 컴포넌트 테스트 인프라 부재) 채팅 UI
컴포넌트에는 테스트를 달지 않는다.
